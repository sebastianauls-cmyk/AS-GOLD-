# Durable complete case analysis

The authenticated `gold-case-roadmap` enqueue action first checks the user's case ownership, current access, consent, readable test-data inputs and normalized output settings. It stores one active job per case. It does not wait for the model and does not store a user session or refresh token. Existing source-only/staged requests remain supported during rollout.

Job status and bounded failure findings are owner-readable through RLS. Request settings and encrypted intermediate candidates live in a private table. An immediate database dispatch, backed by a once-per-minute scheduled recovery sweep, sends the worker a random 244-bit capability for one job. Its SHA-256 hash expires after two minutes and is consumed atomically when a five-minute processing lease is claimed. The worker therefore uses custom authentication and disables the gateway JWT check; the public enqueue action still requires `getUser()` and the existing caller-scoped access checks. None of the machine RPCs is callable by authenticated or anonymous client roles.

The worker advances the existing complete-analysis pipeline one stage per invocation. All three scoped content reviews remain required. It checks current ownership, account state, entitlement, consent and original fingerprint; completion rechecks access and sources. Each successful stage persists a sealed checkpoint before dispatching the next stage. A lost worker lease permits one bounded retry; provider network/timeouts share that retry budget. Content, quota and access rejections do not automatically retry. The original thirty-minute deadline is not renewed, there are at most sixteen successful stages and twenty claimed attempts, and completion inserts the reviewed result with the job ID so stale/replayed workers cannot create duplicates. Terminal jobs erase intermediate candidates. Cancellation invalidates the active lease and prevents subsequent persistence.

The interface restores job status when a case opens and only polls saved state. Closing the page after the accepted-job message does not drive or stop the worker. Document reading/preparation still precedes acceptance; during that phase the page must remain open. Word/PDF export uses the same reviewed result as before. There is no external sending.

Deployment order: apply the core migration, deploy the worker with custom capability authentication, install the scheduler, set the private worker URL and enable dispatch, update the compatible roadmap endpoint, then publish the UI. The scheduler is idle without enabled configuration. No historical case is enqueued automatically by deployment. To pause new work, disable the private dispatch configuration; retain old endpoint sources for rollback.

`test_background_case.mjs` executes the actual SQL migration, leases, access/privacy guards, worker, checkpoints and complete-analysis state machine against PGlite with simulated model and HTTP transport. `test_background_worker_http.mjs` checks the actual worker request handler. The isolated browser fixture verifies leaving/reopening a case, restored failure findings and cancellation. These are engineering checks, not a live Sarah result or professional content acceptance.
